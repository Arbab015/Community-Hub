================================================================================
1. HIGH-LEVEL DATA FLOW
================================================================================

Block/society setup  -->  block_price_ranges (price per marla / size range)
        |
Listing (property/unit) -->  property_listings (sell/rent, price, unit, closed)
        |
Applying a payment plan -->  property_payment_plans (one row per property/unit)
        |                       |-- payment_template_id (nullable: link OR snapshot)
        |                       |-- snapshotted fee/premium values
        |                       |-- listed_price / listed_unit (price snapshot)
        |                       `-- listing_id (legacy link, nullable)
        |
        `-->  property_installment_plans (pivot: one row per attached installment plan)
              (each row is a full snapshot of the installment template's values)
        |
Owner assignment  -->  property_owners (ownership history)
        |              properties.owner_id / property_units.owner_id (current owner)
        |
        |-->  property_ownership_payment_plans  (ONE immutable committed-plan
        |     snapshot per ownership: all payment fields + installment fields +
        |     listed_price/listed_unit + final_price/price_unit; no FK to the
        |     seller's option, so templates/source plans can never alter it)
        |
        `-->  listing marked closed (closed = 1) instead of deleted
              (plan survives via its listed_price snapshot)

KEY MENTAL MODEL:
  - Templates (payment_templates, installment_templates) are NEVER mutated.
  - When a plan or installment is attached/edited, its values are SNAPSHOTTED
    onto the plan row (property_payment_plans) or the pivot row
    (property_installment_plans).
  - At display/calculation time the priority is always:
        plan/pivot row value  -->  linked template value  -->  default/zero

NOTE ON OLD MIGRATION NAMES:
  The pivot table was created as property_payment_plan_installment_templates
  and later renamed (migration 13) to property_installment_plans. Older
  migrations still reference the old name by design - they run BEFORE the
  rename on a fresh install (create -> add columns -> ... -> rename), so they
  must NOT be edited.
  The Eloquent model PropertyPaymentPlanInstallmentTemplate maps to the table
  property_installment_plans (its $table property), and
  PropertyPaymentPlan::installmentTemplates() belongsToMany uses
  'property_installment_plans'.

================================================================================
4. FULL DB WORKFLOWS (END-TO-END)
================================================================================

--------------------------------------------------------------------------------
4.1 BLOCK PRICING SETUP
--------------------------------------------------------------------------------
1. Each block gets one or more block_price_ranges rows:
      block_id | min_size | max_size | price | price_unit
   These define "this block sells at Rs. X per marla/square-yard for plots of
   size Y".
2. Used by:
   - "Apply listing to block" (auto-compute price from area).
   - "Print payment plan" for a given size/type (availability + pricing).

--------------------------------------------------------------------------------
4.2 LISTING A PROPERTY / UNIT
--------------------------------------------------------------------------------
A) Single listing (PropertyListingController::store):
   UPDATE/INSERT into property_listings via listing()->updateOrCreate([], [...]):
     listing_type (sell|rent), price, unit (currency), show_price,
     contact_no, show_contact_no, email, description, closed = false.
   -> Re-listing a CLOSED property resets closed = false (it becomes public again).

B) Block listing (PropertyListingController::blockStore):
   For every owner-less property in the block (optionally filtered by size range):
     - Creates/updates block_price_ranges for the price/range.
     - sell: price = rate x area (marla or square_yard), unit = area unit.
     - rent: price = 0, unit = PKR.
     - closed = false.

--------------------------------------------------------------------------------
4.3 APPLYING A PAYMENT PLAN
--------------------------------------------------------------------------------
A) Single property/unit (PropertyPaymentPlanController::applySingle):
   1. Resolve model by uuid (property or unit).
   2. upsertPaymentPlan():
      - listedPriceValues() snapshots listing.price -> listed_price,
        listing.unit -> listed_unit.
      - If payment_template_id supplied and submitted charges EXACTLY match the
        template -> keep the link (template supplies values at display).
      - If anything differs -> SNAPSHOT every charge/premium onto the plan row
        and set payment_template_id = NULL.
      - Attach installment templates via sync() into pivot
        (property_installment_plans), snapshoting every field.

B) Bulk / block / society apply (PropertyPaymentPlanController::store):
   1. getEligibleProperties(ids, society|block|property, sizeRange, isCommercial):
        query Property whereNull('owner_id'), classify into:
          applied, category_skipped (commercial mismatch), size_skipped (marla).
   2. applyPlan(propertyIds, apply_to_units, paymentTemplateId, installmentIds):
        - each applied property -> upsertPaymentPlan.
        - if apply_to_units -> each unit under those properties whereNull('owner_id').

C) Block default plan (BlocksController::applyBlockPlan):
   BlockPaymentPlan::updateOrCreate(block_id + is_commercial) stores the default.
   Later "apply listing/payment" to the block reuses it.

--------------------------------------------------------------------------------
4.4 EDITING A PLAN / INSTALLMENT (DB side)
--------------------------------------------------------------------------------
A) Plan update (PropertyPaymentPlanController::update):
   - same snapshot-or-link logic as 4.3-A step 2.
   - premiums always snapshotted (never link-only).
   - listed_price / listed_unit re-snapshotted from the current listing.

B) Installment edit (updateInstallment):
   - Sets installment_template_id = NULL.
   - Writes edited values directly onto the pivot row (customized attachment).
   - Source template is untouched.

C) Deleting a plan:
   - PropertyPaymentPlan::deleting() hook deletes its pivot rows first.
   - DB FK also cascades (fk_ppp_id).

--------------------------------------------------------------------------------
4.5 OWNER ASSIGNMENT (PropertyOwnerController::store)
--------------------------------------------------------------------------------
1. Resolve member (existing user or create new Society Member user).
2. Ownership history:
   - Close current open ownerships: property_owners.end_date = today
     (rows where end_date IS NULL).
   - Create new row: start_date = today, end_date = NULL.
3. Set current owner (denormalized):
   - properties.owner_id = user id   (or property_units.owner_id = user id).
4. Snapshot the committed plan (snapshotPaymentPlan, 2026-09-11 change):
   - The seller's plan is NEVER mutated or deleted. "Other plans" and
     "non-given installments" are no longer removed.
   - Create ONE property_ownership_payment_plans row for the new ownership:
     property_ownerable morph (property/unit) + property_owner_id FK (unique) +
     snapshotted payment fields, installment fields, listed_price/listed_unit,
     final_price (= presenter total_price) and price_unit.
   - Values copy rule (2026-09-11): if the plan row (or pivot row) is
     template-linked (payment_template_id / installment_template_id NOT NULL),
     the snapshot is copied from the TEMPLATE first; otherwise the snapshot is
     copied from the plan/pivot row's own values. Blank source values fall back
     to the other source. final_price (= presenter total_price) and price_unit
     are snapshotted too.
     Initially the table has no FK to property_payment_plans / installments so
     deleting templates or source plans can never affect the owner's contract.
5. Listing lifecycle:
   - property_listings.closed = 1   (previously the listing row was DELETED).
   - The payment plan survives because it holds its own listed_price snapshot
     and its listing_id still points at the (closed) listing row.
   - Public front-end queries exclude closed listings
     (whereHas('listing', closed=false) + constrained eager loads), so an owned
     property/unit is no longer shown "for sale".

--------------------------------------------------------------------------------
4.6 DISPLAY / CALCULATION (how stored values are consumed)
--------------------------------------------------------------------------------
PaymentPlanPresenter::build($property) then InstallmentPlanCalculator::calculate().

Value-resolution priority (always):  plan/pivot row  ->  linked template  -> 0.

1) listing_price = plan.listed_price ?? listing.price ?? 0
   listing_unit  = plan.listed_unit ?? listing.unit ?? 'PKR'

2) Premiums (corner / park-facing / boulevard):
   - APPLY ONLY IF the matching feature flag is true on the property
     (is_corner / is_park_facing / is_main_boulevard_facing).
     For a unit, read the flags from its parent property.
   - premium amount = listing_price x premium% / 100.

3) gross = listed_price + premiums_total

4) SURPLUS fees (development, transfer, possession) -> EXCLUDED:
     amount = gross x %/100   (or fixed value);  deducted FROM gross.
     excluded_total = sum of these.

5) NON-SURPLUS fees (booking, down payment, confirmation) -> INCLUDED:
     base = gross;
     amount = base x %/100 (or fixed value);  deducted FROM gross.
     included_total = sum of these.

6) total_price   = gross
   one_time      = excluded_total + included_total
   remaining     = gross - one_time   (amount actually financed)

7) Per installment attachment (pivot row property_installment_plans):
   - extra = additional_installment_amount
             (% of gross if additional_installment_amount_in_per, else fixed)
   - grand_total = remaining + extra
   - balloons:
       - balloon frequency must be LESS frequent than installment frequency
         (monthly < quarterly < biannually < annually). Enforced.
       - total_balloon = % of grand_total (if in_per) OR fixed.
       - balloon_count from frequency math (last event is always a normal
         installment, hence the standard '-1' rule).
       - per_balloon   = ceil(total_balloon / balloon_count)
       - per_installment = ceil((grand_total - total_balloon) / normal_count)
     (ceil = amounts always whole; no fractional payment decimals.)
   - Output: full interleaved schedule (installment/balloon events) with
     running cumulative totals.

FREQUENCY CONSTANTS (InstallmentPlanCalculator):
   installments/year: monthly=12, quarterly=4, biannually=2, annually=1
   balloons/year:     quarterly=4, biannually=2, annually=1


================================================================================
5. RULES / INVARIANTS TO PRESERVE FOR NEXT PAYMENT PLANNING
================================================================================
1. Templates are immutable:
   - Any edit snapshot values onto the plan/pivot and DETACHES the template link.
2. Installment values live on the pivot (property_installment_plans), never on
   property_payment_plans.
3. No fractional payments: per-installment / per-balloon always rounded UP
   (ceil).
4. Balloon frequency must be strictly less frequent than installment frequency.
5. Current owner = denormalized properties.owner_id / property_units.owner_id;
   History       = property_owners (active = end_date IS NULL).
6. Plans apply only to owner-less (whereNull('owner_id')) properties/units.
7. Closed listings (closed=1) are hidden from the public front-end; re-listing
   sets closed=0; owner assignment sets closed=1.
8. A property/unit has no intrinsic price - price is always the listing price
   or the plan's listed_price snapshot.
9. Currency: singular listing unit = currency (PKR/USD/AED/SAR); block listing
   unit = area unit (marla/square_yard). Currency conversion uses
   listed_unit ?? 'PKR'.
10. A plan is linked to a listing by listing_id (nullable) but does not depend
   on it because of the listed_price/listed_unit snapshots.
11. Payment templates and installment templates are scoped per owner_id (user).
    Commercial templates are flagged with is_commercial.
12. property_units use SOFT DELETES; properties do not. Handle both when
    writing future ownership/plan queries.
13. One committed plan per ownership:
    - property_ownership_payment_plans.property_owner_id is UNIQUE.
    - ONE immutable snapshot row per ownership assignment (no FK to the seller's
      option, so source plans, templates, and pivots can be modified or deleted
      without affecting the owner's committed contract).
14. Source plans are never mutated on assignment:
    - snapshotPaymentPlan copies values; it does NOT delete sibling plans or
      prune non-selected installment attachments.  Un-assigning an owner leaves
      the seller's option fully intact for re-use.
15. Template deletion cannot affect ownership payment plans:
    - all fee/premium/installment values are stored as concrete values on the
      snapshot row; the only FKs (to property_owners, property_ownerable morph)
      never depend on templates.
16. Cancel ownership reservation (PropertyOwnerController::cancelReservation, property_owners.cancel_reservation):
    - Ends the CURRENT (open) ownership (end_date = today).
    - Deletes its reserved payment plans snapshot row.
    - Sets properties.owner_id / property_units.owner_id = NULL.
    - Reopens the listing (closed = 0), so it is public again.
    - The seller's source plan + installment pivots are NEVER touched; the
      re-listed property is exactly as it was before the failed sale.
    - UI: "Cancel Ownership Reservation" shows while the current snapshot's
      status is active / in-progress. "Sold Out" badge shows when it is
      'completed' (final sale - no cancellation, no owner assignment).


17. Committed-plan edits never touch the seller's source plan:
    - updateOwnershipPlan (ownership_payment_plans.update) rewrites only the
      charge/premium/listed values and as a side effect recomputes final_price
      from the new snapshot (gross + excluded + extra in case of installment).
    - addOwnershipInstallment (ownership_payment_plans.installment.store)
      attaches ONE installment template by copying its values onto the snapshot
      and sets with_installment = true.
    - updateOwnershipInstallment (ownership_payment_plans.installment.update)
      rewrites the snapshot's single installment block directly.
    - Only a SINGLE installment plan is allowed per committed ownership plan.
    - Balloon frequency must be strictly less frequent than the installment
      frequency (InstallmentPlanCalculator::balloonFrequencyValid).
    - All three routes are permission-gated (payment_plan_edit /
      installment_plan_add / installment_plan_edit).
18. Ownership payment plan tab UI (components/property/ownership-payment-plans):
    - Shown in the Payment Plan tab whenever the current open ownership has a
      committed snapshot with status != 'completed'; the "for sale" planner is
      then hidden and the committed plan is shown instead.
    - Single "Print Owner Plan" button (brief mode only).
    - Summary side shows the whole committed plan; there is NO
      with/without-installment toggle - the installment is appended when present.
    - "Edit Values" opens the whole-plan modal; "Edit Installment Values" opens
      the single-installment modal (with an optional "Load from Template"
      dropdown); "Add Installment Plan" appears only when no installment exists.
