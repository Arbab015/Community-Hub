1. CURRENT SYSTEM OVERVIEW
================================================================================

Your system has these payment-related tables RIGHT NOW:

  payment_templates
  -----------------
  Reusable fee configurations. Example:
    Name: "Commercial Plan A"
    booking_fee: 50000 (fixed)
    development_fee: 5 (% of gross)
    down_payment: 200000 (fixed)
    corner_premium: 2 (% of listed price)
    ...etc

  installment_templates
  ---------------------
  Reusable installment structures. Example:
    Name: "24 Monthly Installments"
    number_of_installments: 24
    installment_frequency: monthly
    additional_installment_amount: 50000 (fixed extra)
    balloon_payment: 10 (% of remaining)
    balloon_payment_frequency: quarterly

  property_payment_plans
  ----------------------
  The ACTUAL plan assigned to a specific property/unit.
  - Links to a payment_template (or custom values)
  - Stores SNAPSHOT values (copied from template at time of apply)
  - Has: listed_price, listed_unit, all fee columns
  - Polymorphic: belongs to Property OR PropertyUnit

  property_payment_plan_installment_templates
  -------------------------------------------
  Pivot table. Each row = one installment plan attached to a payment plan.
  - Links property_payment_plan_id -> installment_template_id
  - Stores SNAPSHOT values (number_of_installments, frequency, etc.)
  - Can be custom (installment_template_id = null)

  property_owners
  ---------------
  Who owns the property. Links owner_id (user) to property via polymorphic.
  - start_date, end_date (null = current owner)


  CURRENT FLOW:
  ┌──────────────┐     ┌──────────────────┐     ┌─────────────────────┐
  │   Property   │────>│ payment_plan     │────>│ installment         │
  │   (owner_id) │     │ (fees snapshot)  │     │ attachments (pivot) │
  └──────────────┘     └──────────────────┘     └─────────────────────┘

  *** NOTHING TRACKS ACTUAL PAYMENTS ***


================================================================================
2. THE PROBLEM
================================================================================

When an owner is assigned:
  - The property's payment plan is used
  - Installment schedule is calculated on-the-fly (not stored)
  - There is NO way to record:
      * "Booking fee was paid on 2026-10-15"
      * "Installment #3 was paid 25,000 on 2026-12-01"
      * "Development fee still pending"
      * "Installment #5 is overdue"

  The entire system is PLANNING only. No PAYMENT TRACKING.


================================================================================
3. WHAT WE NEED TO TRACK
================================================================================

A. ONE-TIME CHARGES (paid upfront, not in installments)
   - Booking Fee, Development Fee, Down Payment, Transfer Fee,
     Confirmation Fee, Possession Fee, Premiums
   - For each: total amount, how much paid, when, by whom, receipt

B. INSTALLMENT PAYMENTS (paid over time)
   - Each installment in the schedule needs:
     * Due date
     * Amount due
     * Amount paid
     * Status (pending / partial / paid / overdue)
   - Individual payment records against each installment

C. OVERALL SUMMARY
   - Total plan amount
   - Total paid (charges + installments)
   - Total remaining
   - Next upcoming payment
   - Overdue count

6. HOW DATA FLOWS (STEP BY STEP)
================================================================================

SCENARIO: Property has a payment plan with:
  - Booking Fee: 50,000 (fixed)
  - Development Fee: 5% of gross
  - Down Payment: 200,000 (fixed)
  - 24 monthly installments of 25,000 each
  - Listed Price: 1,000,000

────────────────────────────────────────────────────────────────────────────────
STEP 1: Admin applies payment plan to property
────────────────────────────────────────────────────────────────────────────────

  Creates: property_payment_plans row
    listed_price: 1000000
    booking_fee: 50000
    development_fee: 5
    development_fee_in_per: 1
    down_payment: 200000
    ...etc

  Creates: property_payment_plan_installment_templates row
    number_of_installments: 24
    installment_frequency: monthly
    ...etc

  NOTHING ELSE HAPPENS. No schedules generated yet. No payments tracked.

────────────────────────────────────────────────────────────────────────────────
STEP 2: Owner is assigned to property
────────────────────────────────────────────────────────────────────────────────

  Creates: property_owners row (owner_id, start_date)
  Updates: property.owner_id

  STILL no schedules. The installment plan is just "attached" — not activated.

────────────────────────────────────────────────────────────────────────────────
STEP 3: Admin generates installment schedule (NEW FEATURE)
────────────────────────────────────────────────────────────────────────────────

  When owner is assigned (or admin clicks "Generate Schedule"):

  Controller reads the installment attachment:
    number_of_installments: 24
    frequency: monthly
    additional_amount: 50000 (extra one-time)
    balloon: 10% quarterly

  Calls InstallmentPlanCalculator::calculate() with:
    listing_price: 1000000
    excluded_charges_total: (development_fee amount)
    included_charges_total: (booking + down_payment amounts)
    additional_amount: 50000
    number_of_installments: 24
    installment_frequency: monthly
    balloon_payment: 10
    balloon_payment_in_per: true
    balloon_payment_frequency: quarterly

  Calculator returns schedule[]:
    [{seq:1, type:'installment', amount:25000, cumulative:25000},
     {seq:2, type:'installment', amount:25000, cumulative:50000},
     {seq:3, type:'balloon', balloon_no:1, amount:100000, cumulative:150000},
     ...]

  Controller creates installment_schedules rows:
    Row 1: seq=1, type=installment, amount=25000, due_date=2026-10-01, status=pending
    Row 2: seq=2, type=installment, amount=25000, due_date=2026-11-01, status=pending
    Row 3: seq=3, type=balloon, amount=100000, due_date=2026-12-01, status=pending
    ...

  Due dates are calculated:
    Start date = today (or next month first)
    Monthly: +1 month each
    Quarterly: +3 months each
    etc.

────────────────────────────────────────────────────────────────────────────────
STEP 4: Owner pays booking fee
────────────────────────────────────────────────────────────────────────────────

  Admin records: "Booking fee 50,000 paid via bank transfer"

  Creates: charge_payments row
    payment_plan_id: 5
    charge_type: booking_fee
    amount: 50000.00
    payment_method: bank_transfer
    receipt_no: RCP-001
    paid_by: (admin user id)
    paid_at: 2026-10-15

  NEXT TIME QUERIED:
    SUM(charge_payments.amount WHERE charge_type='booking_fee') = 50000
    Template says booking_fee = 50000
    50000 >= 50000 → Status: PAID

────────────────────────────────────────────────────────────────────────────────
STEP 5: Owner pays first installment
────────────────────────────────────────────────────────────────────────────────

  Admin records: "Installment #1 — 25,000 paid via cash"

  Creates: installment_payments row
    schedule_id: 1
    amount: 25000.00
    payment_method: cash
    paid_at: 2026-10-01

  Updates: installment_schedules row #1
    amount_paid: 25000.00
    status: 'paid'  (25000 >= 25000)

────────────────────────────────────────────────────────────────────────────────
STEP 6: Owner pays partial installment #2
────────────────────────────────────────────────────────────────────────────────

  Admin records: "Installment #2 — 10,000 paid via online"

  Creates: installment_payments row
    schedule_id: 2
    amount: 10000.00
    paid_at: 2026-11-05

  Updates: installment_schedules row #2
    amount_paid: 10000.00
    status: 'partial'  (10000 < 25000)

────────────────────────────────────────────────────────────────────────────────
STEP 7: Overdue check (cron job or on page load)
────────────────────────────────────────────────────────────────────────────────

  Query: WHERE due_date < CURDATE() AND status IN ('pending', 'partial')

  If any rows found → update status to 'overdue'

  This runs:
    - On dashboard page load
    - Via scheduled artisan command (daily)
    - Or calculated at query time without updating (preferred)

MODEL: InstallmentSchedule
──────────────────────────
  class InstallmentSchedule extends Model
  {
      use HasUuids;
      protected $guarded = [];

      protected $casts = [
          'amount'      => 'decimal:2',
          'cumulative'  => 'decimal:2',
          'amount_paid' => 'decimal:2',
          'due_date'    => 'date',
      ];

      // Relationships
      public function installmentAttachment()
      {
          return $this->belongsTo(
              PropertyPaymentPlanInstallmentTemplate::class,
              'installment_attachment_id'
          );
      }

      public function payments()
      {
          return $this->hasMany(InstallmentPayment::class, 'schedule_id');
      }

      // Helper: is this overdue?
      public function isOverdue(): bool
      {
          return $this->due_date->isPast() && $this->status !== 'paid';
      }

      // Helper: remaining amount
      public function remaining(): float
      {
          return (float) $this->amount - (float) $this->amount_paid;
      }
  }

9. CONTROLLER LOGIC
================================================================================

NEW CONTROLLER: app/Http/Controllers/ChargePaymentController.php
─────────────────────────────────────────────────────────────────

  Methods:
    store(Request $request)     — Record a charge payment
    destroy(ChargePayment $cp)  — Delete a payment record

  store() logic:
    1. Validate: payment_plan_id, charge_type, amount, payment_method, paid_at
    2. Find the payment plan
    3. Calculate total charged for this type:
         $totalCharged = $plan->{charge_type} (from plan or template)
         If percentage: compute actual amount
    4. Calculate total already paid:
         $totalPaid = ChargePayment::where(payment_plan_id, charge_type)
                       ->sum('amount')
    5. If ($totalPaid + $thisAmount) > $totalCharged → reject (overpay)
    6. Create ChargePayment record
    7. Return back with success


NEW CONTROLLER: app/Http/Controllers/InstallmentPaymentController.php
─────────────────────────────────────────────────────────────────────

  Methods:
    store(Request $request)              — Record payment against an installment
    destroy(InstallmentPayment $ip)      — Delete a payment record

  store() logic:
    1. Validate: schedule_id, amount, payment_method, paid_at
    2. Find the schedule row
    3. Calculate remaining: $schedule->amount - $schedule->amount_paid
    4. If $thisAmount > $remaining → reject (overpay)
    5. Create InstallmentPayment record
    6. Update schedule:
         amount_paid += thisAmount
         status = (amount_paid >= amount) ? 'paid' : 'partial'
    7. Return back with success


NEW CONTROLLER: app/Http/Controllers/ScheduleController.php
───────────────────────────────────────────────────────────

  Methods:
    generate(PropertyPaymentPlan $plan)  — Generate installment schedule

  generate() logic:
    1. Check if schedule already exists → skip or regenerate
    2. For each installment attachment on the plan:
         a. Call InstallmentPlanCalculator::calculate() with snapshot values
         b. Calculate due dates starting from today/next month
         c. Create installment_schedules rows for each schedule item
    3. Return back with success

12. EDGE CASES & RULES
================================================================================

  RULE 1: OVERPAY PROTECTION
  ───────────────────────────
  Cannot pay more than the remaining amount for any charge or installment.
  Validation: SUM(payments) + new_payment <= total_amount

  RULE 2: PAYMENT ORDER
  ──────────────────────
  Charges and installments are independent.
  A user can pay booking fee before installments start.
  Installments have their own due dates regardless of charge payments.

  RULE 3: PARTIAL PAYMENTS
  ─────────────────────────
  Allowed for both charges and installments.
  Status logic:
    paid:    SUM(payments) >= total_amount
    partial: SUM(payments) > 0 AND SUM(payments) < total_amount
    pending: SUM(payments) = 0 AND due_date >= today
    overdue: SUM(payments) = 0 AND due_date < today

  RULE 4: PAYMENT DELETION
  ─────────────────────────
  When a payment record is deleted:
    - For charges: no cascade needed (status recalculated on query)
    - For installments: update schedule.amount_paid and recalculate status

  RULE 5: SCHEDULE REGENERATION
  ──────────────────────────────
  If the installment plan is modified (e.g., frequency changed):
    - Existing schedules with payments CANNOT be deleted
    - New schedules are appended
    - Or: admin must clear payments first (with confirmation)

  RULE 6: OWNER TRANSFER
  ───────────────────────
  When ownership changes (old owner removed, new owner assigned):
    - Payment records are KEPT (they belong to the plan, not the owner)
    - New owner sees full payment history
    - Old owner's payment records remain linked via paid_by user

  RULE 7: CURRENCY
  ─────────────────
  All amounts in DECIMAL(15,2) — supports up to 999,999,999,999.99
  Currency is from property_payment_plans.listed_unit (e.g., PKR)
